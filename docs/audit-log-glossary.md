# Audit Log Glossary

This glossary explains the Marmot forensic audit-log terms as Goggles uses
them. It is a reader's guide, not the canonical schema. For exact field
requirements, use `docs/schemas/audit-log-event.v2.schema.json`.

Treat the fields described here as sensitive forensic data. Raw uploads,
bearer tokens, engine ids, account refs, group refs, message ids, payload
digests, IPs, user agents, decrypted content, and transport identifiers should
not be copied into logs, tickets, screenshots, or external systems unless the
recipient is allowed to see them.

## Mental Model

An audit log is JSONL: one JSON object per line. Each line is one audit event.
Each event has two layers:

- Top-level envelope fields, such as `schema_version`, `seq`, `wall_time_ms`,
  `audit_data_mode`, `account_ref`, `engine_id`, and `group_ref`.
- A `kind` object, whose `type` says what happened and whose remaining fields
  are specific to that event type.

Goggles preserves the raw JSONL evidence, then builds relational projections
from it so investigators can read the data by group, message, network path,
convergence run, state change, and evidence line.

## Core Terms

| Term | Meaning |
| --- | --- |
| Audit event | One JSONL line describing something the recorder saw or did. |
| Raw line | The original preserved JSONL line. This is the source evidence. |
| Evidence ref | A pointer back to source evidence, usually file id, line number, line hash, and event kind. Derived rows should link to evidence instead of embedding raw JSON everywhere. |
| `schema_version` | The audit-log schema version. Current logs use `marmot-forensics-audit/v2`; legacy V1 logs are still accepted with restrictions. |
| `seq` | Per-recorder sequence number for ordering events emitted by one recorder session. |
| `wall_time_ms` | Milliseconds since Unix epoch according to the client/engine that recorded the event. Useful for timelines, but it is not a cryptographic ordering guarantee. |
| `recorder_session_id` | Identifier for a recorder session. Mode changes may restart or reopen a recorder session. |
| `audit_data_mode` | Sensitivity mode for the event. `obfuscated_sensitive_data` avoids decrypted content and full identifiers where possible. `full_data` may include decrypted message content, full author ids, and transport wire ids. |
| `account_ref` | Stable obfuscated account reference used for joins. It is sensitive. |
| `engine_id` | The specific account-device engine that emitted the event. One uploaded file should normally contain one engine id. |
| `group_ref` | Stable group reference used to put events into a Goggles group workspace. |
| `context` | Optional event context, such as operation id, source device/account labels, human action, transport, engine, group, or convergence context. |
| `kind` | The event-specific payload. `kind.type` is the event type. |
| Projection | A derived database row built from raw audit events, such as a delivery artifact or convergence run. |
| Quarantine | Storage of invalid or structurally untrustworthy input as preserved evidence, while excluding it from trusted projections where appropriate. |

## Message And Delivery Terms

| Term | Meaning |
| --- | --- |
| Message artifact / delivery artifact | A message-like thing Goggles can trace across engines. It is not only user-visible chat text; it can also be an MLS commit, proposal, welcome, or group info artifact. |
| `artifact_id` / `msg_id` / `message_id` | The canonical Marmot id for a message artifact. For MLS content-bearing artifacts, this is a 64-hex SHA-256 digest of the MLS content bytes. |
| Transport id | A wire-layer id, such as a Nostr event id, gift-wrap event id, welcome rumor id, or key-package tag. These are deliberately separate from `msg_id`. |
| `artifact_kind` | The artifact type: `application_message`, `commit`, `proposal`, `welcome`, `group_info`, or `unknown`. |
| `application_message` | User or app-level payload, such as decoded chat content. |
| `commit` | MLS commit artifact that applies a group-state change. |
| `proposal` | MLS proposal artifact that may later be committed. |
| `welcome` | MLS welcome artifact for a newly added member. Welcome delivery expectations are special: the welcome is expected only by the added member, while existing members receive the commit that adds that member. |
| `group_info` | Metadata or info artifact about the group. |
| Outbound message | An artifact generated by a send or group-create outcome. It may carry recipient expectations and transport metadata. |
| Delivery observation / engine observation | One engine's observed lifecycle for one artifact. |
| State trail | The sequence of states Goggles observed for an artifact on an engine, such as sent, publish acked, received, decoded, failed, or expected. |
| Recipient expectation | A statement of who should receive an artifact, usually based on group membership at a specific epoch. |
| Recipient scope | The shape of the expected recipient set: `all_current_group_members`, `all_other_current_group_members`, `added_member_only`, `explicit_members`, `self_only`, or `unknown`. |
| Recipient matrix | Goggles' comparison of expected recipients against observed engines. |
| `observed` | Goggles has direct evidence that the artifact was observed by the expected engine/member. |
| `missing_inferred` | Goggles expected evidence but did not find comparable observation evidence. This is an inference, not proof of non-delivery. |
| `unobserved_no_uploaded_engine` | The expected recipient has no comparable uploaded engine evidence, so Goggles cannot say much. |
| `observed_not_expected` | An engine observed an artifact that was not in the expected recipient set. |
| `decoded_payload` | Decoded content from the artifact. In `full_data` mode this may include decrypted user-visible content. |
| `decoded_app_event` | Application-protocol details extracted from decoded content, such as app event kind, content, author pubkey, tags, client message id, reply/thread ids, attachments, or raw app event data. |
| Attachment metadata | Optional decoded-app-event metadata about attachments, such as content type, file name, byte length, digest, and app-specific metadata. |
| Peeler | The layer that tries to unwrap, decrypt, or peel incoming transport/application envelopes. |
| Peeler outcome | Result of peeling: `success`, `decrypt_failed`, `stale_epoch`, `malformed`, `invalid_signature`, `wrong_recipient`, or `other`. |
| Rejection | Event explaining why a message/artifact was rejected by processing. |
| Message state | Processing state for an artifact, such as failed, deferred, invalidated, or other MDK-defined states. |

## Network And Transport Terms

| Term | Meaning |
| --- | --- |
| Network observation / transport observation | Evidence about wire movement: publish attempts, publish outcomes, inbound transport receipts, relay metadata, payload digests, and ack status. |
| `transport_received` | A concrete fact that the transport adapter handed an inbound payload to the engine. |
| `ingest_entry` | The engine started ingesting an incoming message/envelope. |
| `ingest_outcome` | The ingest path finished with a specific outcome. |
| `ingest_error` | The ingest path failed before a normal outcome. |
| `publish_attempt` | The engine attempted to publish an outbound artifact. |
| `publish_outcome` | Result of publishing, including accepted relays, failed relays, required ack count, and whether required acks were met. |
| `publish_failure` | Publishing failed before a normal publish outcome. |
| `relay_url` | Transport relay involved in the event. For Nostr-backed transport this is usually a `wss://...` relay. |
| Delivery plane | Logical transport plane or route used for delivery, as named by the client/transport implementation. |
| Transport source | Source adapter or transport implementation that produced the observation. |
| Wire envelope | Transport-layer details such as relay URL, subscription id, wire id, Nostr ids, gift-wrap ids, welcome ids, and publish result id. |
| `wire_id` / `wire_kind` | Generic transport-layer identifier and kind, used when the transport is not represented by a more specific field. |
| `nostr_event_id` / `nostr_kind` | Nostr event identifier and kind for a transport event. |
| `gift_wrap_event_id` | Nostr gift-wrap event id, when the artifact travelled through gift wrap. |
| `welcome_nostr_event_id` | Outer Nostr event id for a transport-level welcome envelope. |
| `welcome_rumor_event_id` | Inner Nostr rumor event id for a gift-wrapped welcome, when available after unwrapping. |
| `welcome_key_package_tag` | KeyPackage e-tag or equivalent welcome target tag linking a welcome to the added member/key package. |
| `payload_len` | Payload length in bytes. |
| `payload_digest` | Payload hash used for correlation without embedding raw payload bytes. Still sensitive. |
| `required_acks` | Number of transport acknowledgements needed for the publish to count as successful. |
| `met_required_acks` | Whether the required acknowledgement threshold was met. |
| Failed relay | Relay-specific publish failure, usually a relay URL plus a reason. |

## State And Epoch Terms

| Term | Meaning |
| --- | --- |
| MLS | Messaging Layer Security, the group cryptography and state protocol Marmot is using. |
| Epoch | MLS group-state version. Commits move the group from one epoch to another. |
| `epoch_confirmed` | A pending epoch transition was confirmed. |
| `epoch_rolled_back` | A pending epoch was abandoned and the engine restored an earlier epoch. |
| `epoch_state_changed` | Engine state-machine transition for an epoch, such as moving to stable, committed, failed, or unrecoverable. |
| Pending commit | Commit/epoch transition that has not yet been confirmed or rolled back. |
| Group state delta | Authenticated durable group-state change derived from `group_state_changed`. |
| `change_kind` | The kind of group-state change: member added/removed/left, admin added/removed, group renamed, topic changed, avatar changed, or message retention changed. |
| Actor | Member or pubkey responsible for a change, when attributable. |
| Subject | Member or pubkey affected by a change, when applicable. |
| `origin_commit_id` | Commit artifact that caused a state delta. |
| Value metadata | Redacted or full details for value-bearing changes, such as digest, length, text, JSON, or pubkeys, depending on audit data mode. |
| Snapshot | Saved group-state snapshot used for recovery, fallback processing, or analysis. |
| Hydration | Reconstructing group state from saved data and events. |
| Hydration quarantined | A group hydration result was set aside because it was suspicious or invalid. |
| Hydration recovered | Hydration recovered from a previously quarantined or failed state. |
| Fork resolution | Decision between an incumbent state and a candidate state/branch. |

## Convergence Terms

| Term | Meaning |
| --- | --- |
| Convergence | The process of resolving competing group-state branches/forks and choosing the branch an engine should treat as canonical. |
| Convergence run | One convergence pass for a group engine. |
| `run_id` | Stable id for a convergence run when MDK emits one. |
| Inferred run | A provisional Goggles grouping of contiguous convergence and epoch-state evidence when MDK did not emit a stable run id. Inferred runs are useful but can be wrong at the boundaries. |
| Phase | Lifecycle state of convergence: `started`, `waiting`, `evaluating`, `selected`, `blocked`, `applied`, `failed`, `stable`, or `unrecoverable`. |
| Candidate branch | One possible group-history branch being evaluated. |
| `branch_id` | Identifier for a candidate branch. |
| Fork epoch | Epoch where the candidate branch diverged. |
| Tip epoch | Latest epoch on the candidate branch. |
| Commit ids | Artifact ids for commits that make up a branch. |
| State digest / tip digest | Hashes used to identify candidate state or branch tips. |
| Retained anchor | Older known point kept so the engine can reason about a branch/fork without rewinding forever. |
| Eligible | Whether a branch is still allowed to win after rule checks. |
| Rejection reasons | Reasons a candidate branch was rejected. |
| Selected branch | Candidate branch chosen by convergence. |
| Losing branches | Candidate branches that were considered but not selected. |
| Score | Structured branch scoring details, such as valid commit depth, effective depth, witness quorum, witness score, tip priority, and tip digest. |
| App witness | Evidence from application-level messages that supports a candidate branch. |
| Rule trace / rule evaluation | Sequence of branch-selection rules, their inputs, their result, and whether each rule was decisive. |
| Decisive rule | Rule evaluation that directly selected or rejected a branch. |
| Auto-commit decision | Event explaining whether the engine decided to commit a proposal automatically and why. |

## Event Family Map

| Family | Event types | What to look for |
| --- | --- | --- |
| Recorder and context | `recorder_started`, `audit_data_mode_changed`, `source_context`, `engine_context`, `group_context`, `recorder_health` | File/session setup, source labels, engine/group metadata, and recorder health. |
| Human action | `human_action` | User or system intent before following message, network, state, or raw evidence. |
| Send and group creation | `send_entry`, `send_outcome`, `send_error`, `create_group_entry`, `create_group_outcome`, `create_group_error` | Local creation of outbound artifacts and create-group results. |
| Network and transport | `transport_received`, `ingest_entry`, `ingest_outcome`, `ingest_error`, `publish_attempt`, `publish_outcome`, `publish_failure` | Whether an artifact was published, acknowledged, received from transport, or ingested. |
| Delivery and processing | `message_content_decoded`, `recipient_expectation`, `peeler_outcome`, `message_state_changed`, `rejection` | Decoded content, recipient expectations, decrypt/peel results, processing states, and failures. |
| Epoch and group state | `epoch_confirmed`, `epoch_rolled_back`, `epoch_state_changed`, `group_state_changed` | MLS epoch transitions and authenticated group-state changes. |
| Recovery and snapshots | `pending_commit_recovered_on_open`, `group_hydration_quarantined`, `group_hydration_recovered`, `snapshot_created`, `fork_resolution` | Recovery paths, state snapshots, hydration health, and fork decisions. |
| Convergence | `convergence_run_state`, `convergence_decision`, `auto_commit_decision` | Branch candidates, selection rules, selected branch, and convergence lifecycle. |

## Common Reading Pitfalls

- A missing observation is usually an inference, not proof. Direct non-arrival
  requires transport/server-side evidence or adapter delivery logs.
- `msg_id` is not a Nostr id. Transport/on-wire ids live in transport fields.
- `full_data` means the event may contain decrypted content or full
  identifiers. Handle it as high-sensitivity forensic evidence.
- One uploaded file should normally contain one `engine_id` and one
  `account_ref`; mixed-engine or mixed-account uploads are structurally
  quarantined because attribution is untrustworthy.
- Projections are conveniences for investigation. The preserved raw JSONL line
  is the evidence of record.
